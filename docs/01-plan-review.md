# TimetableSolver 기획 분석과 개발 전략

분석 대상: `timetable_solver_plan.md.pdf`, v0.1, 2026-11-09, 13쪽.
이 문서에서 **원문**은 첨부 내용, **권고**는 이번 설계 판단, **미확인**은 추가 증거가 필요한 항목이다.

## 1. 제품 판단

개발할 가치가 있다. 자연어 입력, 사용자의 해석 확인, 결정적인 제약 풀이, 불가능 원인의 설명이 하나의 흐름으로 연결된다. 특히 “어떤 조건을 바꾸면 실제로 가능한가”를 보여 주는 기능이 시연과 사용성 양쪽에서 설득력이 있다.

다만 LLM을 붙였다는 사실이나 시간표를 자동 생성한다는 사실만으로 차별성이 입증되지는 않는다. 제품 가치는 다음 사용자 행동으로 검증하는 것이 좋다.

1. 처음 보는 개설강좌 파일을 실제로 올릴 수 있다.
2. 자연어 해석을 사용자가 빠르게 고칠 수 있다.
3. 제시된 후보가 확정한 필수 조건을 모두 지킨다.
4. 불가능한 경우 근거를 보고 수정안을 선택할 수 있다.
5. 다시 계산해도 기존 조건이 의도치 않게 사라지지 않는다.

초기 사용자는 원문의 P1인 **필수 과목과 전공 학점이 뚜렷한 학생**에 집중한다. 교양 탐색, 강의평, 취향 추천까지 넓히면 수업 내용 평가와 추천 품질이라는 별도 문제가 생긴다. 첫 포지셔닝은 “내 조건을 확인하고, 가능한 시간표를 비교하는 도구”가 적합하다.

## 2. 원문에서 유지할 결정

| 원문 결정 | 유지 이유 |
|---|---|
| LLM은 해석, CP-SAT는 선택 | 자연어 처리 오류와 조합 최적화 책임을 분리할 수 있다 |
| 닫힌 제약 스키마 | 지원하지 않는 요구를 임의 코드로 실행하지 않고 명시적으로 거절할 수 있다 |
| 해석 칩을 사용자에게 확인 | “아침”, “가능하면”, “전공”의 의미를 사용자와 합의한다 |
| 학교 포털 크롤링·자동 신청 제외 | 데이터 확보와 수강신청 자동화의 복잡도를 분리한다 |
| 합성 데이터로 시작 | 실제 파일 확보 전에도 알고리즘과 UI를 검증할 수 있다 |
| 3-way 비교와 사용자 평가 | 차별점을 주장 대신 증거로 보여 줄 수 있다 |

## 3. 구현 전에 고칠 문제

### 3.1 이수내역 로컬 전용 정책과 API가 충돌한다

원문 9.3·15절은 이수내역을 서버로 보내지 않는다고 하지만 10절에는 `/profile/parse`와 프로필을 받는 `/solve`가 있다. 외부 LLM으로 이수내역을 파싱하는 내용도 양립하지 않는다.

**권고:** 이수내역은 브라우저에서 TSV/CSV 파싱과 수동 수정으로 처리한다. 브라우저가 `allowed_section_ids`를 계산하고 서버에는 이 목록과 확인된 제약을 보낸다. 원문·성적·학번·제외 사유는 전송하지 않는다. 외부 LLM에는 선호 문장과 필요한 과목/교수 후보만 보낸다.

이 방식도 파생 선호·수강 가능 정보가 서버에 전달되므로 완전한 무전송은 아니다. “이수내역 원본 로컬 보관, 계산에 필요한 파생 정보 최소 전송”으로 제품 설명을 고친다. 파생 정보조차 전송할 수 없다면 로컬 Python 솔버 실행을 선택해야 하며, 브라우저 솔버 이식은 별도 프로젝트 범위다.

### 3.2 hard 위반 0의 범위를 한정해야 한다

원문 1·3·4절은 hard 위반 0을 강조한다. 정확한 제품 표현은 **“지원하는 데이터 형식과 확인된 제약 범위 안에서, 독립 검증을 통과한 후보만 표시한다”**다. 모델링 오류, 잘못된 강의시간, 사용자 의도 오해, 미지원 학교 규칙까지 솔버가 없애 주지는 않는다.

**권고:** OR-Tools와 별개의 순수 Python 검증기를 먼저 작성한다. 서버 반환 직전 검증하며, 실패한 후보는 숨기고 내부 오류를 기록한다. 빈 시간표를 돌려주고 위반 0이라고 주장하는 것을 막기 위해 필수 학점 범위도 사용자에게 확인받는다.

### 3.3 30분 슬롯은 실제 강의시간을 왜곡할 수 있다

원문 8.5절의 30분 슬롯은 09:10~10:25 같은 강의를 정확히 표현하지 못한다. 반올림 방향에 따라 가짜 충돌이나 놓친 충돌이 생긴다.

**권고:** 입력·검증·기본 솔버는 분 단위 정수와 반열린 구간 `[start,end)`를 사용한다. 고정된 강의시간의 겹침을 사전 계산해 충돌하는 분반끼리 동시에 선택하지 못하게 한다. 화면 그리드만 30분 눈금을 사용할 수 있다.

### 3.4 점심 “총 60분 공강”과 “연속 60분 공강”은 다르다

원문 8.5절 식은 점심 구간의 총 빈 시간만 제한한다. 12:00~14:00에서 12:30~13:30 수업이 있으면 30분씩 총 60분은 비지만 식사를 위한 연속 60분은 없다.

**권고:** `lunch_free`는 지정 창 안에 **연속** `min_free_minutes`가 존재한다는 뜻으로 확정한다. 모든 가능한 후보 시작점 또는 충분한 이벤트 경계에서 빈 구간 존재를 모델링한다. 고급 제약 단계에서 구현하고 이 반례를 필수 테스트로 둔다.

### 3.5 공강·연강의 의미가 미정이다

`max_gap`이 가장 긴 한 번의 빈 시간인지, 하루 빈 시간의 합인지 원문은 섞여 있다. 식은 합을 계산한다. 또한 10분 쉬는 시간이 있는 두 수업을 연강으로 보는지도 정해져 있지 않다.

**권고:** `max_gap`은 하루 수업 사이의 **최장 단일 공강**으로 정의한다. 하루 총 공강은 별도 표시 지표다. `max_consecutive`는 `break_reset_minutes` 이상 쉬면 끊기는 수업 체인의 첫 시작~마지막 종료 길이로 정의하고, 초기 제안값 20분을 칩에 명시해 확인받는다. P0에서는 두 기능을 지원하지 않으며 조용히 근사하지 않는다.

### 3.6 후보 다양성 식의 의미가 설명과 다르다

원문 8.6절 `Σ(s∈S*) x_s ≤ |S*|-k`는 이전 후보에서 적어도 k개를 제거하게 한다. 선택 개수가 달라지면 추가만 한 후보를 배제하는 등 대칭적인 “분반 차이”와 일치하지 않는다.

**권고:** 이전 후보와 현재 후보의 대칭차, 즉 Hamming distance를 사용한다. 분반 하나 교체는 거리 2, 하나 추가는 거리 1이다. 화면에도 이 의미를 명시한다. 엄밀한 전역 top-3 대신 **다양성 조건 아래 순차 탐색한 최대 3개 후보**라고 표현한다. 3개가 없으면 실제 개수와 탐색 상태를 반환한다.

### 3.7 불가능과 시간 초과를 분리해야 한다

`UNKNOWN`은 시간 안에 판정하지 못한 상태다. `FEASIBLE`은 유효한 해가 있지만 최적성이 입증되지 않은 상태다. 이를 모두 실패나 최적으로 묶으면 제품의 신뢰성이 훼손된다. 이 상태 구분은 [OR-Tools 공식 문서](https://developers.google.com/optimization/cp/cp_solver)에 근거한다.

**권고:** 첫 풀이가 `INFEASIBLE`일 때만 원래 조건의 불가능 진단을 수행한다. 후보 2를 찾다가 다양성 조건 때문에 `INFEASIBLE`이 된 것은 원래 문제의 불가능이 아니다.

### 3.8 충돌 집합 하나에서 조건 하나를 빼도 해결되지 않을 수 있다

원문은 충분 충돌 집합이 최소 집합이 아닐 수 있음을 잘 적었다. 그러나 독립적인 충돌이 둘이면 어느 한 조건만 풀어도 여전히 불가능하다.

**권고:** 완화안은 항상 재풀이와 검증을 거친 것만 “가능한 수정안”으로 제공한다. 단일 수정에 성공하지 못하면 한정된 복수 수정 탐색을 수행하거나 “탐색 범위에서 수정안을 찾지 못함”으로 표시한다. 자동으로 hard를 soft로 변경하지 않는다.

또한 불가능한 원래 문제에는 유효한 목적함수값이 없다. 원문 F6의 “원래 점수 대비 Δ”는 정의할 수 없다. 대신 수정한 조건 수, 실제 위반량, 공통된 기존 soft 조건 기준의 점수, 검증된 새 시간표를 제공한다.

### 3.9 강도 판별 규칙과 부록 예시가 충돌한다

원문 8.3절은 단서가 없으면 soft라고 하지만 부록의 “전공은 12학점 이상”은 hard다.

**권고:** 명시적 의무·금지·필수·수치 하한/상한을 hard 기본값으로 제안하고, 명시적 희망·가능하면 표현이 해당 절에 있으면 soft를 우선한다. “싫다”만 있으면 soft다. “아침”과 “9시 수업”은 시간 구간 의미를 확인한다. 평가셋도 이 정책으로 일관되게 라벨링한다. 정책은 원문에서 변경한 권고이며 사용자 확인 전에는 실행하지 않는다.

### 3.10 Course와 Section에 들어갈 속성을 분리해야 한다

원문 9.2절은 교수를 Course에 두었다. 실제로 분반마다 교수가 다를 수 있다. `category=전공`도 전필·전선을 집계하는 규칙 없이는 계산할 수 없다.

**권고:** 교수와 강의시간은 Section/Meeting에 둔다. 카테고리는 코드와 명시적 그룹 매핑을 사용한다. 교차개설, 합반, 실습 동시 신청, 격주 수업, 시간 미정은 지원 여부를 표시하며 모르면 추천 대상에서 제외한다. 이수 과목은 현재 개설강좌에 없어도 로컬 프로필에 보존한다.

### 3.11 선호 필터링이 진단 근거를 없앨 수 있다

원문은 시간대 사전 필터링을 제안한다. 금요일 공강 때문에 금요일 수업을 먼저 삭제하면, “필수과목이 금요일에만 개설된다”는 충돌을 복원하기 어렵다.

**권고:** soft 조건으로 분반을 제거하지 않는다. 사용자 hard 조건도 P0에서는 모델에 남긴다. 수강 가능 여부에 따른 제외만 고정 배경 조건으로 처리하고, 제외 이유는 브라우저에서 보존한다. 나중에 최적화할 경우 제거 이유 추적을 필수로 한다.

### 3.12 문자열 검사만으로 설명의 참·거짓은 판별할 수 없다

원문 8.8절의 단어 존재 검사는 “금요일 수업이 있다/없다”처럼 같은 단어를 쓰는 반대 주장을 구분하지 못한다.

**권고:** P0·P1은 계산된 사실과 템플릿으로 설명한다. LLM 문장화는 선택적 확장이다. 확장 시에도 검증된 `fact_id`와 명제 타입을 선택하게 하고 핵심 수치·충족 여부는 코드로 렌더링한다. 실질 가치가 적으면 설명용 LLM을 도입하지 않는다.

## 4. 권장 범위 재조정

| 단계 | 반드시 구현 | 뒤로 미루는 항목 |
|---|---|---|
| P0 기술 MVP | 정규 CSV, 분반·시간 모델, 수동 제약, 기본 hard/soft, 실제 솔버, 독립 검증기, 최대 3개 후보, 상태 구분 | 자연어, 복잡한 공강/연강, xlsx |
| P0 사용자 MVP | 한국어 선호 해석, 확인 칩, 로컬 이수내역, 후보 비교, 템플릿 설명, 충돌 원인과 검증된 단일 완화안 | 임베딩 검색, 설명 LLM |
| P1 공모전 완성 | xlsx 어댑터, 연속 점심·최장 공강·연강, 제한적 복수 완화, 로컬 평가 로그, 비교 평가 | 전 학교 지원, 대규모 서비스 운영 |
| P2 | PNG/ICS, 강의계획서 속성, 공유 기능을 개별 검토 | 졸업요건 자동 보장·자동 수강신청은 계속 제외 |

불가능 진단의 작은 버전은 원문 P1에서 사용자 MVP로 당긴다. 반대로 이수내역 LLM 파싱·설명용 LLM·임베딩을 빼서 구현량을 줄인다. xlsx는 정규 CSV가 돌아간 후 처리한다.

## 5. 기술 선택

- **React + Vite + TypeScript:** 원문 유지. 대화형 시간표 SPA이며 서버 렌더링 필요성이 낮다.
- **FastAPI + Pydantic + OR-Tools:** 원문 유지. 입력 검증, API, 솔버를 한 Python 코드베이스 안에서 분리한다.
- **IndexedDB:** 이수내역과 사용자 초안을 로컬 보관한다. 서버 DB는 초기 범위에 필요하지 않다.
- **Gemini 단일 어댑터:** 초기에는 제공자 한 곳만 연결한다. JSON 구조가 맞아도 의미가 맞는 것은 아니므로 별도 검증을 유지한다. [Google structured output 문서](https://ai.google.dev/gemini-api/docs/structured-output?lang=rest)
- **컨테이너 하나 + 정적 프론트:** 백엔드의 실제 CPU 제약을 측정한다. 초기 배포 후보는 Vercel 프론트 + Render FastAPI이며, 특정 무료 요금제·가격·응답속도를 보장하지 않는다. FastAPI 배포 경로는 [Render 공식 문서](https://render.com/docs/deploy-fastapi)에서 확인했다.
- **제외:** LangChain/LangGraph, 벡터 DB, Redis/Celery, 마이크로서비스, 회원 시스템은 현재 요구에 비해 운영 부담이 크다. 필요가 실제로 생기면 도입한다.

## 6. 일정 제안

1인, 5주 + 1주를 가정한 범위다. Claude Code 사용만으로 개발 기간이 보장되지는 않는다.

| 주차 | 완료 결과 | 진행 판단 |
|---|---|---|
| W1 | 계약·합성 데이터·독립 검증기·기본 솔버·간단한 그리드 | 작은 문제를 전수조사한 정답과 솔버가 일치 |
| W2 | CSV 업로드·수동 제약·soft 점수·후보 비교·시간 초과 UI | LLM 없이 전체 흐름 사용 가능 |
| W3 | 자연어 해석·확인 칩·로컬 이수내역·단일 완화 진단 | 잘못된 해석 수정 및 불가능 복구 데모 가능 |
| W4 | xlsx·고급 시간 제약·필요 시 복수 완화·배포 검증 | 실제 파일 검증 및 대표 반례 통과 |
| W5 | 평가·사용자 관찰·시연 자료 | 실제 수치, 실패 사례, 제한사항 기록 |
| 버퍼 | 안정화·발표·제출 형식 정리 | 기능 추가보다 재현성 확보 |

마감이 짧으면 고급 제약과 xlsx 범용화부터 줄인다. 정확성 검증기, 상태 구분, 해석 확인을 줄이지 않는다. UI를 먼저 전부 완성하기보다 첫 주에 얇은 화면과 실제 솔버를 연결해 가장 위험한 가정을 확인한다.

## 7. 평가를 더 설득력 있게 만드는 방법

**알고리즘 평가와 자연어 평가를 분리한다.** 같은 정답 제약 JSON으로 solver·baseline을 비교하는 실험과, 같은 자연어로 끝까지 처리하는 실험을 따로 둔다. 시스템 C만 사용자 수정을 받았다면 A·B와 동등한 조건이라고 주장하지 않는다. 자동 처리와 사용자 보조 결과를 각각 보고한다.

원문의 100문장은 개발 60 / 검증 20 / 최종 비공개 20으로 나누는 것을 권한다. 마지막 20개는 프롬프트 예시로 쓰지 않는다. 이 표본은 작으므로 수치를 일반화하지 말고 표본 수와 실패 유형을 함께 보여 준다. 문장 복잡도 분포는 가능하면 각 분할에 유지한다.

위반 0만 보면 아무 해도 반환하지 않는 시스템이 유리해진다. **유효해 반환율, hard 위반이 있는 반환 후보 비율, 카탈로그 외 ID 비율, UNKNOWN 비율**을 함께 기록한다. soft 점수는 hard-valid 후보끼리 비교한다. 타임아웃·모델 실패·형식 실패를 분모에서 몰래 빼지 않는다.

50/200/500분반 벤치마크는 CPU·메모리·솔버 버전·worker 수·seed·제약 구성·반복 횟수를 기록한다. `p95 ≤ 2초`는 첫 유효 후보의 warm solve 목표로 한정하고, 파싱·후보 3개·진단·네트워크 포함 전체 시간은 별도로 보고한다. 현재 이 목표는 측정되지 않았다.

사용자 5~8명 실험은 수동→도구와 도구→수동 순서를 나누고 난이도가 비슷한 서로 다른 과제를 써서 학습 효과를 줄인다. 파일 준비 시간도 포함한 결과와 제외한 결과를 구분한다.

## 8. 연구·경쟁 근거의 정리

기획서의 연구 인용 ID를 확인했다. 현재 arXiv 제목은 첫 번째가 [TRACE-CS: A Hybrid Logic-LLM System for Explainable Course Scheduling](https://arxiv.org/abs/2409.03671), 두 번째가 [DCP-Bench-Open: Evaluating LLMs for Constraint Modelling of Discrete Combinatorial Problems](https://arxiv.org/abs/2506.06052)이다. 기획서 표기와 달라 제출 시 제목·버전을 맞춰야 한다.

TRACE-CS는 논리 추론과 LLM을 결합하는 관련 연구로 인용할 수 있다. 원문에 적힌 100%와 44~49%는 이번 검토에서 논문 본문의 해당 실험표까지 재검증한 수치가 아니므로 발표에 그대로 옮기지 않는다. 연구별 과제·평가 조건이 달라 본 서비스의 예상 성능으로 사용할 수도 없다.

SNUTT·빈틈의 최신 기능 전체를 이번 검토에서 조사한 것은 아니다. 따라서 “다른 서비스에는 자동 생성이 없다” 대신 이 제품에서 직접 입증한 기능과 검증 결과로 차별점을 설명한다.

## 9. 개발 시작 전·실데이터 연결 전 확인할 항목

개발 자체는 제안 기본값으로 시작할 수 있다. 다음은 실제 사용자용 정확성 주장 전에 확인해야 한다.

- 실제 개설강좌 파일의 열·인코딩·교시 표기와 합법적으로 사용할 수 있는 범위.
- 학기·요일·특수 수업시간·채플 등 고정 일정·격주 강의·실습 동시 신청의 존재.
- 복수전공 등에 따른 카테고리 분류 기준과 재수강·선수과목 인정 규칙.
- 개발 인원·공모전 실제 마감·LLM 비용 상한·데모 환경.
- 파생 수강 가능 목록을 서버에 전송하는 제안에 맞춘 실제 제품 고지.

학교 규칙을 모르는 상태에서는 “지원 범위 안의 시간 충돌 및 사용자가 확인한 조건을 검증”했다고 표현한다. 실제 수강 가능·졸업 가능·좌석 확보를 보장하지 않는다.
