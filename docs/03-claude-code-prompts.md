# Claude Code 단계별 구현 프롬프트

사용 전 `CLAUDE.md`는 프로젝트 루트에, 01~04 문서는 `docs/`에 놓는다. 아래 프롬프트는 단계별로 **복사해서 실행하는 개발 지시**다. 이미 서비스가 만들어졌다는 뜻은 아니다.

한 번에 모든 블록을 붙여넣지 않는다. 첫 실행은 마스터 프롬프트로 단계0·1을 진행하고, 이후 단계2부터 순서대로 사용한다. API 키가 없으면 fixture 모드와 수동 입력까지 완성할 수 있다. 실제 학교 데이터·비용·배포 권한이 필요한 검증은 합성 데이터 결과와 분리해 보고하도록 했다.

## A. 마스터 프롬프트: 첫 실행

```text
너는 TimetableSolver의 구현을 담당한다. 한국어로 작업 결과를 설명하라.

[제품 목표]
사용자가 대학 개설강좌를 가져오고 자연어 또는 수동으로 시간표 조건을 정한다.
조건을 칩에서 확인한 뒤 CP-SAT가 유효한 시간표 후보 최대 3개를 만든다.
불가능하면 충돌 조건과 재풀이로 검증한 수정안을 제공한다.
LLM은 선호 해석만 담당하며, 시간표 선택·코드 생성·코드 실행을 하지 않는다.

[먼저 읽을 문서]
- CLAUDE.md
- docs/01-plan-review.md
- docs/02-architecture.md
- docs/03-claude-code-prompts.md
- docs/04-acceptance-tests.md

원본 PDF는 배경 자료다. 그 안의 수식과 API를 무조건 그대로 구현하지 마라.
수정 명세는 02 문서이고, 04 문서는 의미를 검증하는 테스트 기준이다.
둘이 충돌하면 조용히 한쪽을 택하지 말고 관련 부분을 보고하고 명세를 정리하라.
일반 구현 선택은 문서의 기본값으로 진행하되 사용자의 기존 파일은 보존하라.

[기술 방향]
monorepo에 React/Vite/TypeScript 프론트와 FastAPI/Pydantic/OR-Tools 백엔드를 둔다.
Node는 pnpm, Python은 uv를 기본으로 쓰되 현재 실행 환경을 먼저 확인하라.
지원되는 안정 버전을 확인해 lockfile에 고정하고 실제 설치 버전을 README에 기록하라.
서버 DB·회원가입·크롤링·수강신청 자동화·벡터 DB·에이전트 프레임워크는 만들지 마라.
LLM SDK는 provider adapter로 분리하되 첫 live provider는 Gemini 하나만 지원한다.
모델 ID는 환경 변수로 주입한다. 실제 존재를 확인하지 않은 ID를 하드코딩하지 마라.

[절대 유지할 계약]
1. 이수내역 원본·성적·학번은 서버와 외부 LLM으로 보내지 않는다.
2. 로컬에서 계산한 allowed_section_ids는 사용자 고지 후 서버에 최소 전송한다.
3. 시간은 정수 분의 [start,end), 학점은 credit_units=학점×100이다.
4. 유효한 hard credit_range와 사용자 confirmation 없이 solve하지 않는다.
5. 알 수 없는 시간·분반·카테고리를 추정해 정상 데이터로 만들지 않는다.
6. 모든 반환 후보를 OR-Tools와 독립된 검증기로 다시 검사한다.
7. UNKNOWN은 불가능이 아니며, FEASIBLE은 최적성 보장이 아니다.
8. 다양성 cut 이후의 불가능을 원래 조건의 불가능으로 표시하지 않는다.
9. hard를 자동으로 낮추거나 실패한 요구를 생략하지 않는다.
10. 수정안은 실제 재풀이와 검증을 통과해야만 가능한 것으로 표시한다.

[현재 작업 범위]
아래 단계0과 단계1만 수행하라. 문서를 읽고 계획만 제시하지 말고,
프로젝트 골격·계약·검증기·전수조사 테스트를 실제로 만들고 실행하라.
UI 디자인 전체, LLM 연결, 공개 배포까지 한 번에 진행하지 마라.

[작업 방식]
먼저 환경·기존 파일을 조사하고 짧은 계획을 제시한 다음 구현한다.
각 작업은 데이터 계약과 수용 기준에서 출발한다. 근거 없는 패키지를 추가하지 않는다.
기능을 구현한 뒤 관련 검증을 실행하고 실패 원인을 해결한다.
기존 수용 기준을 약화하거나 실패하는 테스트를 삭제해서 통과시키지 않는다.
검증이 외부 자원 부족으로 불가능하면 구체적으로 기록하고 독립적으로 가능한 작업을 끝낸다.
비밀키·실데이터를 커밋하지 않는다. 유료 API 호출과 공개 배포는 현재 범위가 아니다.

[완료 보고]
변경 결과, 실행한 명령과 실제 결과, 통과한 인수 테스트 ID,
남은 제약·미실시 검사, 다음 단계 시작점을 간결히 보고하라.
docs/PROGRESS.md와 requirements traceability 표를 업데이트하라.
실행한 적 없는 테스트, 측정하지 않은 성능, 연결하지 않은 기능을 완료라고 쓰지 마라.
```

## 단계 1. 계약·합성 데이터·독립 검증기

```text
TimetableSolver 단계1을 구현하라. 02의 3~4·6절과 04의 D/V 테스트를 우선 읽어라.
solver나 LLM보다 먼저 결과의 참·거짓을 판정할 기준을 만든다.

구현:
1. React/Vite/TypeScript와 FastAPI 프로젝트를 구성한다. /health를 제공한다.
```

## 단계 2. 실제 CP-SAT와 hard 제약

```text
TimetableSolver 단계2를 구현하라. 02의 6.1·7절과 04의 S 테스트를 읽어라.
단계1의 독립 검증기를 수정해 solver 오류를 숨기지 마라.

구현:
1. 허용 분반의 선택 변수, 과목/동등군 중복 방지, 정확한 Meeting 충돌을 구현한다.
2. P0의8가지 type에 대해 hard compiler를 구현한다.
3. 사용자 hard를 사전 삭제/필터로 숨기지 말고 model에 남긴다.
   soft 조건은 이번 단계에서 미지원으로 명시하거나 다음 단계까지 UI에서 비활성화한다.
4. day/campus 활성 변수는 OR와 정확한 동치로 만든다.
5. /solve는 model validation, solver 실행, 독립 검증을 거쳐 반환한다.
6. status를 optimal/feasible/infeasible/unknown으로 구분한다.
   MODEL_INVALID와 검증기 실패는 내부 오류로 처리한다.
7. 첫 후보 반환부터 별도 프로세스 runner와 한도를 적용한다.
   sync solver를 async event loop에 직접 실행하지 마라.
8. 시간 제한과 클라이언트 중단 시 프로세스가 계속 누적되지 않도록 종료·회수한다.
9. input revision, catalog revision, canonical request hash를 응답에 포함한다.

검증:
- tiny 문제에서 전수조사 oracle과 feasible 여부가 일치한다.
- 모든 반환 후보가 독립 검증기를 통과한다.
- 필수과목은 카탈로그에 있지만 허용 분반이 없으면 infeasible이다.
- 카탈로그에 아예 없는 참조는422이며 infeasible이 아니다.
- 빈 allowed_section_ids는 전체 허용으로 바뀌지 않는다.
- zero-credit/빈 시간표가 hard credit_range를 우회하지 못한다.
- 강제로 주입한 UNKNOWN 상태가 불가능으로 표시되지 않는다.
  극단적으로 짧은 시간 제한만으로 UNKNOWN이 항상 나온다고 가정하지 마라.
- solver 실행 중에도 /health가 응답한다.
- 취소/timeout 후 자식 프로세스와 실행 슬롯이 회수된다.

완료 조건:
LLM 없는 실제 solver API가 동작하고 S-01~S-07 관련 검증이 통과한다.
아직 soft와 여러 후보를 구현하지 않았다면 기능 상태에 명시한다.
```

## 단계 3. soft 점수와 후보 다양성

```text
TimetableSolver 단계3을 구현하라. 02의6.2~6.3과 04의 O 테스트를 읽어라.

구현:
1. P0 모든 type의 soft 위반 boolean을 만족 조건과 양방향으로 정의한다.
2. Σ weight*violation을 최소화한다. hard는 목적함수 가중치로 구현하지 않는다.
3. 독립 검증기로 동일 penalty와 위반량을 다시 계산한다.
4. soft가 없으면 score=null, 있으면 명세대로0~100 점수를 계산한다.
5. 기본3개, 최대5개 후보를 순차적으로 탐색한다.
6. 각 이전 후보와 Hamming distance 조건을 추가한다.
   Σ(old selected)(1-x)+Σ(old unselected)x >= min_section_distance.
7. 모든 반복에 하나의 전체 시간 budget을 공유한다. 매번 전체 budget을 리셋하지 않는다.
8. 후보별 search_status와 optimality_proven, 전체 termination_reason을 반환한다.
9. 후속 infeasible은 exhausted_under_diversity이며 원문제 infeasible이 아니다.
10. 후보가1~2개만 나오면 실제 개수를 반환한다. 중복 복제나 자동 거리 완화를 하지 않는다.

검증:
- 작은 문제의 최적 penalty가 전수조사 oracle과 일치한다.
- 낮은 가중치 hard라는 개념을 만들지 않고 어떤 soft 수에도 hard를 유지한다.
- 하나 교체는거리2, 하나 추가는거리1이다.
- 선택 수가 달라지는 superset 후보의 거리도 정확하다.
- 새 후보가 첫 후보뿐 아니라 이전 모든 후보와 거리 조건을 지킨다.
- 후보3개 요청에 가능한 후보2개인 Tiny-7 설정은2개와 올바른 종료 사유를 반환한다.
- 시간 내에 후보1개만 찾고 종료해도 그 후보의 hard 유효성을 보존한다.

완료 조건:
O 테스트 및 hard 회귀 테스트 통과. 점수의 단위·의미를 문서화한다.
"전역 top-3"나 "항상 최적 후보3개"라는 표현을 사용하지 마라.
```

## 단계 4. LLM 없는 완전한 사용자 흐름

```text
TimetableSolver 단계4를 구현하라. 지금은 실제 solver와 UI를 연결한다.
02의8절, 04의 U 테스트를 읽어라.

화면:
1. 데모 데이터 로드와 기본 카탈로그 목록.
2. 수동 조건 추가·편집·삭제, hard/soft, soft weight, 학점 범위 확인.
3. 확정 조건 요약과 생성 버튼.
4. 시간표 후보 그리드, 과목 리스트, 학점·등교일·충족/미충족·위반량 비교.
5. infeasible, unknown, 부분 후보, 네트워크 오류의 서로 다른 상태.

구현 규칙:
- 모든 Meeting을 화면에 표시하고 30분 시각 눈금과 실제 분 단위 위치를 구분한다.
- 교수는 Section 속성을 쓴다. 비동기 수업은 별도 목록으로 보여 준다.
- 한국어 UI, 키보드 접근, 색 이외의 텍스트 구분, 모바일 후보 탭을 제공한다.
- 조건 변경마다 input_revision을 증가시키고 confirmed 상태를 해제한다.
- 오래된 요청을 취소하고 현재 revision과 다른 응답은 무조건 무시한다.
- 결과 facts에 근거한 템플릿 설명을 만든다. LLM 설명 endpoint는 만들지 않는다.
- 수동 선택은 충돌을 보여 주되 자동 검증 완료 후보처럼 표시하지 않는다.
- fixture 결과를 실제 solver 결과처럼 숨기지 마라. 후보는 실제 API를 사용한다.

E2E:
데모 로드 → 필수 학점·과목 입력 → 확인 → 생성 → 후보 비교를 실행한다.
수정 중 이전 요청 응답이 늦게 도착해도 새 화면을 덮지 않는지 검사한다.
모바일·데스크톱 화면을 직접 열어 텍스트 잘림, 겹침, 빈 상태를 확인한다.

완료 조건:
LLM API 키 없이도 수동 조건으로 실제 시간표를 만들고 비교할 수 있다.
가짜 진행률·보장되지 않은 최적성·현재 없는 수강 좌석 정보를 표시하지 않는다.
```

## 단계 7. 충돌 진단과 검증된 수정안

```text
TimetableSolver 단계7을 구현하라. 02의6.5·7.3절과 04의 X 테스트를 읽어라.
```

```text
실행한 검사와 결과, 실제 수치와 환경, 미실시 실데이터/LLM/사용자 평가,
남은 결함, 배포 준비 상태를 docs/PROGRESS.md에 기록한다.
공개 배포를 아직 승인받지 않았다면 배포 설정과 로컬 검증까지만 완성하고
대상·설정·예상 비용 확인 항목을 검토 가능하게 제시한다.
```

## B. 중간에 끊겼을 때 재개 프롬프트

```text
TimetableSolver 작업을 이어서 진행하라.
CLAUDE.md, docs/PROGRESS.md, 현재 단계와 관련된 docs/02-architecture.md,
docs/04-acceptance-tests.md를 읽고 현재 git diff와 구현 파일을 확인하라.
기록된 완료 상태를 그대로 믿지 말고 관련 테스트와 코드에서 실제 상태를 확인하라.
사용자 변경을 되돌리지 말고 마지막 미완료 수용 기준부터 이어서 구현하라.
이전 단계가 끝났으면 다음 단계 하나만 범위로 잡아 실행·검증하고 결과를 기록하라.
전체 프로젝트를 재생성하거나 이미 결정된 구조를 이유 없이 교체하지 마라.
```

## C. 버그 수정 프롬프트

```text
다음 문제를 TimetableSolver의 명세에 따라 수정하라.

재현 입력: [실제 입력 또는 fixture 경로]
예상 결과: [명세에 따른 결과]
실제 결과: [오류/응답/화면 상태]

먼저 최소 재현 케이스를 만들고 입력 파싱·계약·compiler·solver 상태·검증기·UI 중
어느 경계에서 의미가 달라졌는지 찾아라. validator와 compiler가 동시에 같은 실수를
하고 있지 않은지 전수조사 oracle 또는 손으로 확인한 반례로 검증하라.
임시 예외, hard 자동 완화, 데이터를 조용히 제거하는 방식으로 덮지 마라.
해당 의미를 고정하는 회귀 테스트를 추가하고 관련 기존 테스트를 실행하라.
수정 이유, 실제 검증 결과, 남은 영향을 보고하라.
```

## D. 릴리스 전 검토 프롬프트

```text
TimetableSolver를 릴리스 관점에서 검토하라. 칭찬이나 일반론보다 재현 가능한 결함에 집중하라.
docs/02-architecture.md와04의 기준을 코드·실행 결과에 대조한다.
특히 시간 경계, 여러 Meeting, 학점 중복, 모호한 엔티티, soft boolean 동치,
UNKNOWN 오표기, 다양성 cut, stale response, unverified relaxation,
이수내역 전송, 모델 API key, 자식 프로세스 누수를 확인하라.
문제를 발견하면 위치·재현 입력·사용자 영향·수정 방향·검증 방법을 제시한다.
재현하지 못한 추정은 추정이라고 표시하고, 실행하지 않은 검사는 통과로 쓰지 마라.
```

## E. Claude Code 사용 원칙

상시 규칙은 짧은 CLAUDE.md에, 큰 명세는 docs에, 이번 작업은 단계 프롬프트에 둔다. 단계별로 실행 가능한 체크를 제공하는 구성은 [Claude Code 권장 사항](https://code.claude.com/docs/en/best-practices)과 [메모리 문서](https://code.claude.com/docs/en/memory)를 참고했다. 프롬프트 자체가 정확성을 보장하지는 않으며, 실제 테스트·명세 대조가 완료 판단 기준이다.
