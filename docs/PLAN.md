# TimetableSolver (가칭) 기획서

> 자연어 선호를 제약으로 변환하고, 솔버로 풀어 근거와 함께 시간표를 제시하는 서비스

- 버전: v0.1 (2026-11-09)
- 작성: 윤성현
- 출품 후보: 2026 한동 AI·SW 페스티벌 / 스마트 소프트웨어 공모전 – SW전공 부문
- 형태: 웹 앱 (시연 가능한 MVP)
- 표기: `[가설]` = 측정으로 검증할 목표, `[확인 필요]` = 외부 정보·결정이 필요한 항목

---

## 1. 개요

**한 줄 요약**
"금요일 공강, 9시 수업 싫음, 전공 12학점 이상"이라고 쓰면, LLM이 이를 제약으로 변환하고 CP-SAT 솔버가 충돌 없는 시간표 후보를 만들어 근거와 함께 보여준다. 조건이 불가능하면 어떤 조건이 충돌하는지와 완화안을 제시한다.

**핵심 아이디어**
- LLM은 이해와 설명만 한다. 분반 선택은 솔버가 한다.
- LLM 출력은 닫힌 스키마(JSON)로 제한하고, 사용자가 해석 결과를 확인한 뒤에만 풀이한다.
- hard 제약 위반 0을 구조적으로 보장하고, 이를 LLM 단독 방식과 정량 비교한다.

## 2. 배경 및 문제 정의

### 2.1 Pain Point
- 수강신청 전 시간표 구성은 후보 분반을 수동으로 조합하는 작업이다.
- 선호가 다차원이다. 공강 요일, 시간대, 점심, 연강 한도, 교수, 학점, 카테고리 최소 학점이 동시에 걸린다.
- 조합이 많아 사람이 최적에 가까운 해를 찾기 어렵고, 불가능한 조건 조합은 시도해 본 뒤에야 알게 된다.
- 범용 챗봇에 개설강좌를 붙여넣어도 환각, 충돌, 개설되지 않은 분반 제안이 나올 수 있다.
- `[가설]` 시간표 구성에 의미 있는 시간이 쓰인다. 사전 설문(5–8명)으로 확인한다.

### 2.2 주요 사용자
- **P1. 전공 중심 3–4학년**: 필수·선택 학점 요건과 선호 시간대를 함께 만족시켜야 한다.
- **P2. 교양을 탐색하는 저학년**: 카테고리 균형, 공강 요일, 시간대 선호가 중심이다.

### 2.3 현재 대안과 한계 (검색 확인 범위)
- 수동 조합형 시간표 앱: 태그·빈 시간대 검색으로 강좌를 추가한다 (예: SNUTT). 선호 기반 자동 생성은 확인하지 못했다.
- 시간표 사진 분석형: 시간표 이미지를 AI로 읽고 그룹의 공통 공강을 계산한다 (예: 빈틈). 시간표를 짜 주는 도구는 아니다.
- 범용 LLM 직접 생성: 규모가 커지면 제약 위반과 환각 위험이 있다. `[가설]` 이를 실험으로 측정한다.

## 3. 차별점과 근거

| 축 | 내용 |
|---|---|
| 보장 | 해가 나오면 hard 제약 위반 0 (솔버 구조상 성립) |
| 설명 | 불가능 시 충돌 집합과 완화안 + 비용 제시 |
| 신뢰 | LLM 해석을 사용자가 칩으로 확인 후 풀이 |
| 도메인 | 한국 대학 도메인 제약 어휘 (공강, 점심, 연강, 카테고리, 교수 선호 등) |
| 증거 | LLM 직접 생성 / LLM+코드 실행 / 본 시스템 3-way 정량 비교 |

**학술적 근거**
- TRACE-CS: SAT로 제약을 인코딩하고 LLM으로 질의를 처리한다. 설명 정확도가 100%였고 LLM 단독은 44–49%였다 (설명 정확도 기준이며 본 과제에 그대로 적용되는 수치는 아니다).
- LLM으로 자연어를 CP-SAT 모델로 바꾸는 연구가 존재한다. 본 설계는 모델 코드를 생성시키지 않고 닫힌 스키마를 사용해 신뢰성을 높인다.

**정직한 한계**
- 구조 자체는 새롭지 않다. 가치는 도메인 어휘, 확인 UX, 불가능 진단, 평가 증거에 있다.
- 개설 분반이 적고 일회성 사용이면 범용 챗봇으로도 충분할 수 있다. 우위는 규모, 보장, 반복 수정에서 나온다.

## 6. 사용자 시나리오

**S1. 선호 입력으로 후보 생성**
1. 개설강좌 파일과 이수내역을 올린다.
2. "금요일 공강, 오전 9시 수업 싫음, 전공 12학점 이상, 점심시간 비우기"를 입력한다.
3. 시스템이 "이렇게 이해했어요" 칩 5개를 보여준다. 사용자는 한 칩의 강도를 soft에서 hard로 바꾼다.
4. 후보 3개가 나오고, 각 후보에 충족·미충족 제약이 표시된다.

**S2. 불가능 조건 진단**
1. "교수 A 과목 필수"를 추가한다.
2. 해가 없다고 알리고 충돌 원인을 제시한다 (금요일 공강 ↔ 필수 과목이 금요일에만 개설).
3. 완화안 2개 (금요일 공강을 soft로, 대체 분반 허용)와 각 비용을 보여준다.

**S3. 반복 수정**
1. 후보 중 하나가 마음에 들지만 "수요일 연강이 길다"고 판단한다.
2. `max_consecutive` 제약을 추가하고, 기존 조건은 그대로 두고 재계산한다.

## 8. AI·알고리즘 설계

### 8.1 파이프라인
```
[개설강좌 CSV] ──┐
[이수내역 텍스트] ─┼─> 정규화·검증 ─> Catalog / Profile
[선호 문장] ──> LLM(NL→JSON) ─> 스키마 검증 ─> 엔티티 매칭 ─> 확인 칩(사용자)
                                                          │
                                       확정된 Constraints ▼
                         후보 필터(이수·선수) ─> CP-SAT 모델 ─> top-N 해
                                                          │
                                   불가능 → assumption core → 완화안
                                                          ▼
                     LLM(설명 문장화, 솔버 사실만 입력) ─> 후검증 ─> UI
```

### 8.2 제약 어휘 (닫힌 집합)
| type | 의미 | 예시 params |
|---|---|---|
| credit_range | 총 학점 범위 | {min, max} |
| must_include / must_exclude | 과목 포함/제외 | {course_id} |
| day_off | 공강 요일 | {days[]} |
| time_avoid / time_prefer | 시간대 회피/선호 | {days[], start, end} |
| max_gap | 하루 내 공강 최대 | {minutes} |
| lunch_free | 점심 구간 확보 | {start, end, min_free_minutes} |
| max_consecutive | 연강 최대 | {minutes} |
| max_days_on_campus | 등교 요일 수 상한 | {days} |
| category_min | 카테고리 최소 학점 | {category, credits} |
| instructor_avoid / instructor_prefer | 교수 선호 | {instructor} |

모든 제약 공통 필드: `id, type, params, strength(hard|soft), weight(1–10), source_text`.

### 8.3 NL → 제약 변환
- Gemini/GPT structured output으로 위 스키마를 강제하고 pydantic으로 검증한다.
- 강도 판별 규칙:
  - hard 단서: "무조건", "꼭", "반드시", "절대" 등
  - soft 단서: "~면 좋겠다", "가능하면", "웬만하면" 등
  - 단서가 없으면 soft로 두고 칩에서 사용자가 조정한다.
- 모호성 처리: 시간대 표현("아침", "저녁")처럼 기준이 불명확하면 기본 해석을 칩에 명시하고 되묻는다.
- 모순 감지: 같은 대상에 상반된 제약이 들어오면 충돌 경고를 띄운다.
- LLM에게는 시간표를 직접 만들게 하지 않는다.

### 8.4 엔티티 매칭
- 과목명·교수명은 정확 일치 → fuzzy → 임베딩 순으로 `course_id`/`instructor_id`에 매핑한다.
- 신뢰도가 낮거나 후보가 여럿이면 선택지를 제시한다. 자동 확정하지 않는다.

### 8.5 CP-SAT 모델
**변수**
- 분반 선택 $x_s\in\{0,1\}$
- 슬롯 점유 $o_{k,t}$ (요일 $k$, 30분 슬롯 $t$)

**기본 제약**
- 과목당 최대 1분반: $\sum_{s\in c}x_s\le 1$
- 시간 충돌 방지: $o_{k,t}=\sum_{s:\,(k,t)\in T_s}x_s\le 1$
- 학점 범위: $L\le\sum_s cr_s\,x_s\le U$
- 이수 과목, 선수 미충족 과목은 후보 분반에서 사전 제외한다.
- `must_include(c)`: $\sum_{s\in c}x_s=1$. 해당 과목이 개설되지 않았다면 사전에 불가능으로 보고한다.

**파생 변수와 제약**
- 공강일: $d_k\ge o_{k,t}$ ($\forall t$), 등교일 수 $=\sum_k d_k$
- 하루 첫·마지막 수업 슬롯: $o_{k,t}\Rightarrow \text{first}_k\le t,\ \text{last}_k\ge t$. 최소화 압력에서 값이 타이트하게 잡힌다.
- 공강 슬롯: $\text{gap}_k=\text{last}_k-\text{first}_k+1-\sum_t o_{k,t}$ (수업이 있는 날만)
- 연강 한도: 길이 $W{+}1$ 슬라이딩 윈도우마다 $\sum o\le W$
- 점심 확보: 점심 구간 $\Lambda$에서 $\sum_{t\in\Lambda}o_{k,t}\le|\Lambda|-F$
- 카테고리 최소 학점: $\sum_{s\in cat}cr_s x_s\ge m$

**목적함수**
$$\max\ \sum_j w_j\,u_j\;-\;\sum_k w_k\,p_k$$
- $u_j$: soft 제약 충족 지시변수, $p_k$: 위반 정도(슬랙)
- 가중치는 1–10 입력을 정규화해 사용한다.

### 8.6 후보 다양성
- 이전 해 $S^*$마다 no-good cut을 추가한다: $\sum_{s\in S^*}x_s\le|S^*|-k$.
- 이 조건으로 후보 간 서로 다른 분반이 $k$개 이상 되게 한다.

### 8.7 불가능 진단
- hard 제약마다 assumption literal을 만들고 `only_enforce_if`로 활성화한다.
- 해가 없으면 `sufficient_assumptions_for_infeasibility`로 충돌 제약 집합을 얻는다.
- 충돌 집합의 각 제약을 하나씩 해제하고 재풀이해 "X를 풀면 해 존재 (목적함수 Δ)"를 완화안으로 제시한다.
- 최소성 보장은 하지 않는다 (충분 집합이며 최소 집합이 아닐 수 있음).

### 8.8 설명 생성
- 입력: 솔버가 확정한 사실 (선택 분반, 충족/미충족 제약, 위반량, 충돌 집합).
- LLM은 이를 자연어로 바꾸기만 한다.
- 후검증: 설명에 등장하는 과목명·요일·시간이 결과 JSON에 존재하는지 문자열로 점검한다. 불일치하면 템플릿 설명으로 대체한다.

### 8.9 (Stretch) 강의계획서 속성 추출
- PDF → {팀플 여부, 시험 비중, 출석 반영} + 근거 문장 span.
- 결과는 soft 속성 (`team_project_avoid` 등)으로만 사용하고 hard로 쓰지 않는다.

## 9. 데이터 설계

### 9.1 입력 파일 (개설강좌)
권장 열: `course_code, course_name, section, credit, category, instructor, day, start, end, room, prerequisite`
- 한 분반이 여러 시간 블록을 가지면 행을 분리하거나 `meetings` 열로 구분한다.
- `[확인 필요]` 한동 수강신청 시스템에서 내려받을 수 있는 실제 형식과 열 이름. 샘플 한 건으로 파서를 확정한다.

### 9.2 내부 스키마
```json
Course  {"id":"CSE301","name":"웹서비스개발","credit":3,"category":"전선","instructor":"..."}
Section {"id":"CSE301-01","course_id":"CSE301",
         "meetings":[{"day":"Tue","start":"10:30","end":"12:00"}],"capacity":40}
Profile {"taken":["CSE101"],"in_progress":["CSE201"],
         "credits_by_category":{"전필":18,"전선":9,"교양":24}}
```

### 9.3 이수내역 파싱
- 포털 이수내역 표를 붙여넣는다 → 결정론적 파서 + 열 매핑 UI로 `{code?, name, credit, term, category?}` 추출 → 카탈로그에 매칭 → 신뢰도 낮은 행은 확인 칩.
- 파서가 실패하는 형식에 한해 LLM 파싱을 fallback으로 둔다. 사용자 동의 후, 브라우저에서 과목코드·과목명·학점 열만 추려 전송한다 (성적·학번·이름은 전송하지 않음).
- 성적은 입력받지 않는다. 필요한 것은 이수 여부, 학점, 카테고리뿐이다.
- 재수강/F/P는 "이수 인정 여부" 플래그 하나로 처리한다.
- 이수내역 원본은 브라우저 로컬(IndexedDB)에만 저장한다. 서버로 전송되는 것은 선호 문장, 카탈로그(비개인), 그리고 fallback 사용 시 동의된 최소 열이다.

## 10. 시스템 구성

**스택**
- Frontend: React + Vite + TypeScript, 시간표 그리드 컴포넌트
- Backend: FastAPI + OR-Tools(CP-SAT) + pydantic
- LLM: Gemini 또는 OpenAI API (structured output)
- 저장: 클라이언트 IndexedDB. 서버는 stateless (DB 선택)
- 배포: Vercel(프론트) + Render 또는 AWS EC2(백엔드) `[결정 필요]`

**API**
- `POST /catalog/validate` — 개설강좌 검증·정규화
- `POST /profile/parse` — 이수내역 파싱
- `POST /constraints/parse` — 선호 문장 → 제약 JSON
- `POST /solve` — 제약 + 카탈로그 + 프로필 → 후보 N개 또는 불가능 진단
- `POST /explain` — 솔버 사실 → 설명 문장

## 11. UI 구성

1. **데이터 준비**: 개설강좌 업로드 + 열 매핑, 이수내역 붙여넣기 + 확인.
2. **선호 입력**: 자연어 입력창 + 해석 칩 목록 (강도 토글, 가중치 슬라이더, 삭제, 수동 추가).
3. **후보 비교**: 시간표 그리드 카드 3개, 후보별 충족/미충족 요약, 선택 이유 설명.
4. **진단 패널**: 불가능 시 충돌 제약 강조, 완화안 버튼 (적용 시 비용 표시).
5. **확정/내보내기**: 최종 시간표 보기, PNG/ICS (P2).

디자인 원칙: 시간표 그리드를 먼저 구현하고 충돌 표시를 수동 선택에서도 사용한다. 이후 솔버를 붙인다.

## 12. 평가 계획

### 12.1 NL→제약 변환
- **평가셋**: 선호 문장 100개 (단일 30, 복합 40, 모호 20, 모순 10). 수집은 직접 작성 + 지인 5–8명 작성분. 정답 JSON은 직접 라벨링하고 일부(20%)를 재검증한다.
- **지표**: constraint-level precision/recall/F1, hard/soft 구분 정확도, 엔티티 매칭 정확도, 되묻기 적절성.
- **ablation**: few-shot 유무, 단서 규칙 유무.

### 12.2 3-way 비교 (핵심 증거)
같은 카탈로그·프로필·선호 문장 세트에서 비교한다.
- (A) LLM 직접 생성: 카탈로그를 컨텍스트에 넣고 시간표 생성을 요청.
- (B) LLM + 코드 실행: 코드 실행으로 직접 풀게 함.
- (C) 본 시스템.

지표:
- hard 위반율 (자동 검증기로 판정)
- 카탈로그에 없는 분반 제안 비율
- soft 충족도 (가중 합)
- 불가능 케이스에서 올바르게 "불가능"으로 판정한 비율
- 응답 시간

카탈로그 규모를 50 / 200 / 500 분반으로 달리해 성능이 어느 지점에서 갈리는지 본다.

### 12.3 솔버 성능
- p50/p95 풀이 시간, 후보 다양성, 불가능 판정 시간.

### 12.4 사용자 평가
- 5–8명, within-subject: 수동 구성 vs 도구 사용.
- 측정: 소요 시간, 만족도(Likert 5), 후보 채택 여부, 해석 칩 수정 횟수.
- 소규모이므로 통계적 주장 대신 사례와 분포를 보고한다.

## 15. 개인정보·윤리·AI 활용 명시

- 이수내역 원본은 브라우저에서만 처리·저장한다. 서버(LLM 포함)로 전송하는 것은 선호 문장과 개설강좌 정보이며, 이수내역 LLM fallback 사용 시에는 동의된 최소 열만 전송한다. 선호 문장이 외부 LLM으로 전송됨을 UI에 고지한다.
- 실험 로그는 사용자 동의 후에만 수집하며 익명화한다.
- 포털 로그인·자동 신청 기능은 만들지 않는다.
- **공모전 제출용 AI 활용 내역 (초안, `[확인 필요]` 실제 사용 도구로 갱신)**
  - 개발 과정: 코드 작성·리팩터링·테스트 생성에 AI 코딩 도구 사용 (도구명, 활용 범위 기록).
  - 서비스 내: LLM API를 선호 해석, 이수내역 파싱, 설명 문장화에 사용. 시간표 결정은 솔버가 담당.

## 부록 A. 선호 문장 → 제약 예시

**입력**: "금요일엔 수업 없었으면 좋겠고, 아침 9시 수업은 절대 싫어. 전공은 12학점 이상. 점심은 꼭 비워줘."

```json
[
 {"id":"c1","type":"day_off","params":{"days":["Fri"]},
  "strength":"soft","weight":7,"source_text":"금요일엔 수업 없었으면 좋겠고"},
 {"id":"c2","type":"time_avoid","params":{"days":["Mon","Tue","Wed","Thu","Fri"],"start":"09:00","end":"10:00"},
  "strength":"hard","weight":10,"source_text":"아침 9시 수업은 절대 싫어"},
 {"id":"c3","type":"category_min","params":{"category":"전공","credits":12},
  "strength":"hard","weight":10,"source_text":"전공은 12학점 이상"},
 {"id":"c4","type":"lunch_free","params":{"start":"12:00","end":"13:00","min_free_minutes":60},
  "strength":"hard","weight":10,"source_text":"점심은 꼭 비워줘"}
]
```
- "전공"이 카탈로그의 어떤 category 값(전필+전선 등)에 대응하는지는 칩에서 사용자가 확정한다.

## 부록 B. 데모 시나리오 (3분)

1. 샘플 학기의 개설강좌와 이수내역을 불러온다. (20초)
2. 선호 문장을 입력하고 해석 칩을 확인·수정한다. (40초)
3. 후보 3개를 비교하고 선택 이유를 읽는다. (40초)
4. "교수 A 과목 필수"를 추가해 불가능 상태를 만든다. (20초)
5. 충돌 근거와 완화안을 확인하고 하나를 적용한다. (30초)
6. 같은 입력에 대한 LLM 직접 생성 결과와 위반 건수를 나란히 보여준다. (30초)
